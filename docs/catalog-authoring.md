# Connector Catalog Authoring Guide

This guide explains how to update the deployment-authoritative connector inventory,
how the `catalog-check` CI gate works, and how to fix it when it fails.

## Background

The file `deployment/catalog/connector-inventory.pb` is a deterministic binary
protobuf that enumerates every connector available to the AstraSync compiler. It
is committed to the repository and consumed by the control plane at runtime. Any
change to a connector's descriptor — adding a new connector, changing
capabilities, adding options, or updating the artifact version — must update this
file, or the CI gate will fail.

The inventory is generated by the `catalog-export` CLI subcommand using a
deterministic canonical form (connector names sorted, options sorted, SHA-256
content-addressed). Two inventories generated from the same descriptor set are
byte-for-byte identical regardless of machine or JVM version.

## When to Regenerate

Regenerate the catalog when you change any connector descriptor, add a new
connector, remove a connector, or update `ConnectorRegistry.java` to include or
exclude a connector.

You do **not** need to regenerate the catalog when:
- You change connector runtime code that does not affect the descriptor.
- You change connector test code.
- You change the Helm chart, Go control plane, or anything outside the
  `connector-api/` and `connectors/` trees.

## Quick Reference

```bash
# 1. Regenerate the committed catalog against the current commit
make catalog-export

# 2. Verify the change is correct
make catalog-info

# 3. If catalog-check (CI) fails locally, diagnose the difference
python scripts/diff-catalog.py deployment/catalog/connector-inventory.pb target/connector-inventory.pb

# 4. Stage and commit the new catalog bytes
git add deployment/catalog/
git commit -m 'chore: update connector inventory'
```

## Adding a New Connector

1. **Implement the connector** under `connectors/connector-<name>/`. Follow the
   connector SPI contract (`docs/connector-dev.md`).
2. **Register the connector** by adding its factory to the Java service loader file
   at `connector-api/src/main/resources/META-INF/services/io.astrasync.connector.api.ConnectorFactory`
   and/or to `engine/src/main/resources/META-INF/services/io.astrasync.connector.api.ConnectorFactory`.
3. **Add the descriptor** — the `ConnectorDescriptor` returned by the factory
   is auto-discovered by `ConnectorRegistry.discover()`.
4. **Regenerate the catalog**:

   ```bash
   make catalog-export
   ```

5. **Verify** the new connector appears:

   ```bash
   make catalog-info
   # Expected: look for the new connector name in the output
   ```

6. **Commit**:

   ```bash
   git add deployment/catalog/
   git commit -m 'feat(connector): add <name> connector to deployment catalog'
   ```

## Modifying an Existing Connector

If you change a connector's descriptor — for example, adding a new option,
changing the delivery guarantee, or updating the artifact version — the catalog
must be regenerated to reflect the change:

```bash
make catalog-export
git add deployment/catalog/
git commit -m 'fix(connector): update <name> descriptor (options/capabilities/delivery)'
```

## Understanding catalog-check Failures

When `catalog-check` (or CI) reports a failure, it means the committed catalog
does not match what the current code would produce. There are three causes:

### 1. Descriptor drift (genuine change)

The committed catalog is stale because you changed a connector descriptor but
forgot to regenerate. Fix: `make catalog-export` and commit the new bytes.

### 2. Build-version drift (expected)

The `--compiler-build` field differs because the current commit's SHA is
different from the SHA embedded in the committed catalog. This is **expected** on
every new commit; the catalog-check CI step uses the git SHA to produce
deterministic output. If the diff-catalog output shows only `compiler_build`
and `compiler_revision` changing with all descriptors identical, run:

```bash
make catalog-export
git add deployment/catalog/
git commit -m 'chore: re-bake connector inventory against current commit'
```

### 3. Non-determinism (regression)

Both the committed and freshly-exported catalogs have the same git SHA but
different bytes. This is a regression in `ConnectorInventories.deterministicBytes`.
File a bug and temporarily regenerate with `make catalog-export`.

## The catalog-export Command

```bash
# Uses git SHA as build version and standard execution profile
make catalog-export

# Override build version for a specific release
CATALOG_BUILD_VERSION=v0.2.0 make catalog-export

# Override execution profile
CATALOG_EXECUTION_PROFILE=minimal make catalog-export

# Specify output path
CATALOG_OUTPUT=/tmp/my-catalog.pb make catalog-export
```

### Environment variables

| Variable | Default | Description |
|----------|---------|-------------|
| `CATALOG_BUILD_VERSION` | `$(git rev-parse --short HEAD)` | Build identifier embedded in the catalog |
| `CATALOG_EXECUTION_PROFILE` | `standard` | Execution profile (affects descriptor set) |
| `CATALOG_OUTPUT` | `target/connector-inventory.pb` | Output file path |

## Inspecting the Catalog

```bash
# Summary of the committed catalog
make catalog-info

# Diff two catalog versions
python scripts/diff-catalog.py deployment/catalog/connector-inventory.pb target/connector-inventory.pb

# With explicit jar override (if CLI jar is not in the default location)
python scripts/catalog-info.py --jar /path/to/astrasync-cli.jar
```

## CI Gate Details

The `Check deployment connector inventory` job in `.github/workflows/ci.yml`:

1. Builds the CLI (`mvn -pl cli -am package -DskipTests`)
2. Exports the catalog using `${{ github.sha }}` as `--compiler-build`
3. Compares with the committed `deployment/catalog/connector-inventory.pb`
4. On failure: runs `scripts/diff-catalog.py` and prints diagnostics to the CI log

The git SHA approach ensures that:
- The embedded `compiler_build` always reflects the commit that produced the catalog
- A version bump (e.g. 0.1.0-SNAPSHOT → 0.2.0-SNAPSHOT) does not cause spurious failures
- Build-version-only drift is reported separately from descriptor drift

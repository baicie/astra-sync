# Phase 31 — Tenant-Id Envelope Cross-Module Chain Test

## Status

Active (ADR-076 Accepted — §2 superseded by ADR-080; ADR-079
Accepted — superseded on public-surface by ADR-080; ADR-080
Accepted. The cross-module chain test fixture ships with five

## Goal

Extend the tenant-id envelope regression surface from
**single-module chain** (Phase 30, ADR-075 — Console-side BFF egress
↔ Console CR dual-write) to **cross-module chain** — pinning the
join between the Console BFF, the API Server interceptor, the
mutation repository, and the PostgreSQL `astrasync_control_jobs.
tenant_id` column, in a single test binary.

This phase is test-only. No production code, no schema migration,
no metric, no RBAC change. The existing module boundaries are
preserved: console does not import api-server, and api-server does
not import console.

## What ships in Phase 31

A new top-level module under
`tests/cross-module/chain-tenant-id/` with:

```
tests/cross-module/chain-tenant-id/
├── go.mod                          # standalone module, replace directives
├── go.sum                          # generated by go mod tidy
└── chain_test.go                   # 5 cases (see §Test coverage)
```

The new module's `go.mod` declares:

```go
module io.astrasync/tests/cross-module/chain-tenant-id

go 1.26

require (
    io.astrasync/console v0.0.0
    io.astrasync/control-plane/api-server v0.0.0
)

replace (
    io.astrasync/console => ../../console
    io.astrasync/control-plane/api-server => ../../control-plane/api-server
)
```

This matches the existing `tests/e2e/` pattern (a separate
multi-module workspace).

## Test coverage

Five cases, each pinning a single chain step:

| Test | Boundary crossed | Asserts |
| --- | --- | --- |
| `TestCrossModule_ChainMatchesBFFScopeAndAPIServerMutation` | BFF egress **and** API Server interceptor **and** mutation repository | a single mutation call: BFF `scope.tenantID` == `x-astra-tenant-id` metadata == `Mutation.TenantID` == `repo.GetMutation(uid).TenantID` |
| `TestCrossModule_APIServerRejectsBFFMismatch` | BFF egress **and** API Server rejection | `x-astra-tenant-id = T1` against principal membership for `T2`; api-server rejects with `codes.PermissionDenied` and emits `TENANT_DENIED` audit |
| `TestCrossModule_APIServerRejectsMalformedMetadata` | BFF egress **and** envelope validation | non-UUID `x-astra-tenant-id`; api-server rejects with `codes.PermissionDenied` and emits `TENANT_ENVELOPE_INVALID` |
| `TestCrossModule_NoTenantIDInMetadataFallsBackToMembership` | BFF egress (omitted) **and** API Server fallback | no metadata; api-server derives from membership and writes that to `repo.GetMutation(uid).TenantID` |
| `TestCrossModule_APIServerMigration003PersistsVerifiedTenantID` | API Server interceptor **and** mutation repository **and** migration `003_jobs_tenant_id.sql` | after migration applies, `repo.GetJob(uid).TenantID` matches the metadata-declared tenant-id |

Each test gets its own subtest with a fresh fixture so failures
attribute to a single chain step.

## Fixture design

The cross-module fixture is **in-process** and **deterministic**:

1. **In-process gRPC server** running `*grpc.Server` with the real
   `JobService` registered against the real `authn.Interceptor`.
2. **Real interceptor** (no test stub), so `withJobTenantID` actually
   attaches the verified tenant-id to the request context.
3. **In-memory `Memory.Repository`** for the api-server's
   PostgreSQL dependency. The test asserts on `Memory` directly.
4. **BFF client adapter** that invokes the same handler code path
   the HTTP server invokes
   (`s.mutations.CreateJob(ctx, key, spec, idemKey)`) with
   `metadata.AppendToOutgoingContext(ctx, "x-astra-tenant-id", ...)`.
   No HTTP server is instantiated.

The fixture is **purpose-built** for the tenant-id envelope
contract; it does not attempt a generic cross-module test
framework.

## Migration test fallback

`TestCrossModule_APIServerMigration003PersistsVerifiedTenantID`
covers the live migration `003_jobs_tenant_id.sql`. The default
implementation uses a **migration SQL parse + dry-run** assertion
that verifies the migration is applied via the project's existing
`migrations.Manager.Apply` interface against the in-memory adapter.

If the project later adopts `testcontainers-go` (or already uses
`dockertest`), the test may be upgraded to run against a real
PostgreSQL instance without changing the test's contract.

The fallback decision is recorded in ADR-076 §7 and is not deferred
to a follow-up ADR.

## CI integration

A new job `cross-module-chain-tenant-id` ships under
`.github/workflows/cross-module-chain-tenant-id.yml` (separate from
the existing `phase30-chain-tenant-id-regression.yml` so that each
phase's envelope gate is independently triggerable).

Trigger matrix:

- `pull_request:` only when the diff includes `console/`,
  `control-plane/api-server/`, `control-plane/job/`,
  `docs/phase31/`, or `tests/cross-module/chain-tenant-id/`
  (path filter via `paths:`).
- `push: branches: [main, develop]` — post-merge envelope gate.
- `workflow_dispatch` — manual on-demand re-run.
- **No schedule** — the existing
  `phase30-chain-tenant-id-regression.yml` already provides nightly
  coverage of the chain; cross-module chain tests are slower
  (~5s vs <1s) and don't need to re-run nightly.

The cross-module test does **not** replace the per-module
`interceptor_test.go` and `chain_e2e_test.go`. Layered test
surface:

1. **Boundary-level** (existing, per module):
   `interceptor_test.go` (api-server) +
   `bff_slice28_test.go` (console) +
   `bff_slice28b_test.go` (console) +
   `syncjob_emission_test.go` (controller).
2. **Single-module chain** (Phase 30, ADR-075):
   `chain_e2e_test.go` (console, BFF egress ↔ Console CR dual-write).
3. **Cross-module chain** (Phase 31, this phase):
   `tests/cross-module/chain-tenant-id/` (BFF ↔ api-server ↔
   mutation repository).

## Non-Goals (this phase)

- **No production code change.** Phase 31 is test-only.
- **No controller module.** The full chain Console → API Server →
  PostgreSQL → Controller → metric emission is a Phase 32
  follow-up; importing the controller module into the cross-module
  fixture is a separate dependency decision (see ADR-076
  Follow-ups).
- **No live PostgreSQL by default.** The migration test uses the
  dry-run parse fallback unless the project adopts testcontainers.
- **No new RBAC, no new helm resource, no new metric.**
- **No new top-level dependency in `console` or `api-server`.**

## Notes on scope

The fixture reflects ADR-080 §1: the cross-module test exercises
the **join** between the BFF and the api-server's public gRPC
surface, not the api-server interceptor itself (which is pinned
by `control-plane/api-server/internal/authn/interceptor_test.go`
on Layer 1 of the layered test surface). The five cases were
recast from "interceptor rejects" to "BFF ingress contract" per
ADR-080 §4.

## Follow-ups (out of scope for Phase 31)

- **Phase 32**: extend the cross-module fixture to cover the full
  chain Console → API Server → PostgreSQL → Controller → metric
  emission. This requires importing the controller module into the
  cross-module fixture, which is a separate dependency decision.
- **Live migration test**: replace the dry-run fallback with a real
  `testcontainers-go` PostgreSQL instance for the migration test
  case.
- **Cross-region checkpoint push chain** (ADR-052) reuses the
  same fixture pattern; separate ADR.

## Rollback

The phase is test-only. Removing
`tests/cross-module/chain-tenant-id/` and the new CI workflow file
reverts the slice with no production code impact.

# ADR-057: v0.3.0 Release Cut (Phases 13-16)

## Status

Accepted

## Context

`CHANGELOG.md` currently has three sections:

- `## [Unreleased]` — contains Phase 13 (Kubernetes production hardening),
  Phase 14 (ArgoCD GitOps), Phase 15 (catalog lifecycle automation), and
  Phase 16 (CI / test hygiene & release tooling).
- `## [v0.2.0] - 2026-09-07` — Phase 1 through Phase 12.
- `## [v0.1.0-phase0] - 2026-08-02` — initial MVP.

Every phase README from Phase 1 through Phase 16 is marked `**Complete.**`
The release dry-run script (`scripts/release-dry-run.py`) already passes
for the current commit. Maven `pom.xml` still declares `0.1.0-SNAPSHOT`
and Helm `Chart.yaml` still declares `0.2.0`, both lagging behind the
content that needs to ship.

Phase 16 added the tooling required to make a release cut low-risk
(`scripts/release-dry-run.py`, `scripts/check-changelog.py`, the
`check-docs` CI job). The tooling is in place but no release decision
has been recorded.

## Decision

### 1. Cut `v0.3.0`

Promote the current `## [Unreleased]` content into a new
`## [v0.3.0] - 2026-09-07` section. Phases 13-16 ship together because
they form a coherent delivery: production hardening (13), GitOps (14),
catalog lifecycle (15), and CI/test hygiene tooling (16) all land in the
same Kubernetes-operable artifact.

A new empty `## [Unreleased]` placeholder is appended so future slices
have a known drop zone. The `scripts/check-changelog.py` guard will
flag any drift on the next commit.

### 2. Bump the project version

`pom.xml`: `0.1.0-SNAPSHOT` → `0.3.0`. This is a stable release version,
not a `-SNAPSHOT` qualifier; the next post-release commit will move the
version back to a `-SNAPSHOT` qualifier per Semantic Versioning.

`deployment/helm/astrasync/Chart.yaml`: `0.2.0` → `0.3.0`. Both
`version` (the chart version) and `appVersion` (the application
version) move in lockstep because the chart has not introduced any
chart-only breaking change since `0.2.0`.

### 3. Release dry-run is the gate

`make release-dry-run` must pass before this ADR is accepted. The
script:

- Reads the Maven version from `pom.xml` (now `0.3.0`).
- Reports the git HEAD that would be embedded in the catalog build id.
- Lists every Complete phase (1, 3, 4, 5, 6, 8-16) and confirms each one
  is referenced in `## [Unreleased]` or an earlier versioned section
  (the exemption rule from `scripts/check-changelog.py` continues to
  exempt Phases 1-12 that shipped under `v0.2.0`).
- Reports the tracked proto file inventory (7 files).

If `release-dry-run` fails, the cut is rejected and the underlying
drift must be fixed before retrying.

### 4. Tagging is left to the maintainer

This ADR does not push a `v0.3.0` git tag. Tagging is the maintainer's
release-day action because:

- The `Dockerfile*` matrix in `.github/workflows/ci.yml` references
  `astrasync/<image>:ci` only; release-tag-driven image publishing is a
  separate workflow decision.
- The Operator CRD generation step (`make crd-generate`) is currently
  wired into `ci.yml` as a check, not a publish step.
- The release process should leave room for the maintainer to inspect
  the diff between `v0.2.0` and `v0.3.0` and decide whether to
  publish images, Helm chart OCI artefacts, or both.

The maintainer's checklist:

1. `make release-dry-run` exits 0.
2. `make check` exits 0 (`vet-go + check-runbooks + check-docs +
   spotless:check`).
3. Tag `v0.3.0` against the current commit.
4. Bump `pom.xml` back to `0.3.0-SNAPSHOT` on the next development
   commit (post-release housekeeping, not part of this ADR).

### 5. CHANGELOG coverage rule

The `scripts/check-changelog.py` guard is extended by **policy**, not
by code: Phases 13-16 are exempt from the `[Unreleased]` reference
requirement once `v0.3.0` ships because their content lives in a
versioned section. The guard already implements this exemption via the
`phase_number <= 12` rule; we extend the exemption boundary to
`phase_number <= 16` in `scripts/check-changelog.py` at the same
commit so that future releases do not need to touch the guard.

## Consequences

### Positive

- `v0.3.0` is the first release whose contents match its version; the
  Maven, Helm, and CHANGELOG surfaces are all in sync.
- The Phase 16 release tooling gets exercised end-to-end on this cut,
  validating that `release-dry-run` actually catches drift.
- The 27 dependabot PRs (#52-#78) waiting behind PR #77 can finally
  rebase against a `main` that contains the Phase 13-16 content.

### Negative

- Bumping `pom.xml` to a non-`-SNAPSHOT` version means the next
  development commit must remember to flip it back to
  `0.3.0-SNAPSHOT`. The release-dry-run guard catches the inconsistency,
  but it is an extra commit of housekeeping.
- The `chart` version bump is coupled to the `appVersion` bump. Future
  chart-only changes will need a separate ADR that distinguishes the
  two version fields (out of scope for this slice).

## Alternatives Considered

### Skip the `v0.3.0` cut and keep accumulating in `[Unreleased]`

Reject. The Phase 16 hygiene tooling was built precisely to make
release cuts auditable and reproducible; deferring it makes the
tooling unused. The repo also has open PRs that depend on a
`main` containing Phase 13-16 content.

### Cut separate `v0.3.0`, `v0.4.0`, `v0.5.0` releases for each phase

Reject. Phases 13-16 form a coherent "Kubernetes-operable platform"
delivery; splitting them into four releases would force downstream
operators to roll forward four times for what is one logical artifact.
The CI workflow changes between Phase 13 and Phase 16 mean a
mid-Phase-14 release would not have the production profile step.

### Auto-bump versions on release via a `make release` target

Reject for this slice. A `make release` target that mutates `pom.xml`,
`Chart.yaml`, and `CHANGELOG.md` would benefit future releases but is
out of scope for the current tooling pass. The maintainer's manual
checklist is the smallest viable process for the first release cut
that exercises the new tooling.

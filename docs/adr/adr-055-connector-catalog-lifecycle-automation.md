# ADR-055: Connector Catalog Lifecycle Automation

## Status

Accepted

## Context

`deployment/catalog/connector-inventory.pb` is a deterministic binary protobuf
generated by `cli catalog-export`. The CI pipeline (`.github/workflows/ci.yml`)
and `Makefile` both re-export the catalog and assert byte-for-byte identity
with the committed copy. Three concrete problems limit the catalog lifecycle
today:

1. **Hardcoded `--compiler-build 0.1.0-SNAPSHOT`.** Both `Makefile catalog-check`
   and `ci.yml Check deployment connector inventory` pass
   `--compiler-build 0.1.0-SNAPSHOT --execution-profile standard`. The CLI's own
   default (`AstraSyncCli.VERSION = "AstraSync 0.1.0-SNAPSHOT"`) is overridden
   in three places. When the project bumps its version to 0.2.0-SNAPSHOT the
   hardcoded strings will be wrong and `catalog-check` will fail spuriously
   even when the actual descriptor set has not changed, because the
   `compiler_build` field embedded in the binary is stale.

2. **CI failure gives no diagnostics.** When `catalog-check` fails,
   `scripts/check-files-identical.py` only reports `files differ`. The developer
   cannot tell whether the failure is due to:
   - a genuine descriptor change they need to commit,
   - a build-version drift unrelated to the descriptor set, or
   - a non-deterministic export (regression in `ConnectorInventories.deterministicBytes`).

   They have to manually run `protoc --decode` or write throwaway code to
   inspect the binary.

3. **No standalone catalog inspection tool.** A developer who wants to know
   "what connectors are currently in the catalog?" or "what is the inventory
   revision?" has to either compile the CLI jar, run it, parse the binary,
   or look at the binary header. There is no `make catalog-info` target.

4. **No documentation for the author flow.** A contributor adding a new
   connector under `connectors/<name>/` has no documented procedure to update
   `deployment/catalog/connector-inventory.pb`. The existing
   `connector-spi.mdc` says "must `make catalog-check`" but does not say what
   to do when it fails or how to regenerate.

## Decision

### 1. Dynamic compiler build version

The `--compiler-build` flag is sourced from the git commit SHA (short form)
at catalog-export time, not from a hardcoded literal.

```makefile
CATALOG_BUILD_VERSION ?= $(shell git rev-parse --short HEAD 2>/dev/null || echo unknown)
CATALOG_EXECUTION_PROFILE ?= standard

catalog-check: catalog-export
	python scripts/check-files-identical.py \
		deployment/catalog/connector-inventory.pb \
		target/connector-inventory.pb
```

The same value flows into the CI step:

```yaml
- name: Check deployment connector inventory
  env:
    CATALOG_BUILD_VERSION: ${{ github.sha }}
  run: |
    make catalog-check
```

The committed `.pb` continues to embed whatever build SHA was current when
it was last regenerated; the gate now passes if and only if the descriptor
set under `connector-api/`, `connectors/`, `engine/plan/ConnectorRegistry.java`
matches the committed inventory at the current commit.

### 2. Readable catalog diff

A new `scripts/diff-catalog.py` parses both `.pb` files using the
`google.protobuf` text format (`protoc --decode_raw`) or, when the Python
protobuf runtime is available, the structured descriptor list, and prints
a unified diff of:

- `compiler_build`, `compiler_revision`, `inventory_revision`,
  `execution_profile`, `job_spec_schema` (header-level fields)
- `descriptors[*].name` (additions / removals)
- `descriptors[*].options[*]` (option set diff)

The script exits 0 if the catalogs are equivalent in descriptor set, non-zero
otherwise. The CI `Check deployment connector inventory` step invokes it on
failure so the developer sees the diff inline in the CI log.

### 3. Standalone catalog inspection

A new `scripts/catalog-info.py` reads one `.pb` and prints a human-readable
summary:

```
inventory_revision: sha256:abc123…
compiler_revision:  sha256:def456…
compiler_build:     a1b2c3d
execution_profile:  standard
job_spec_schema:    sync.astrasync.io/v1
descriptors:        4
  - csv        (delivery=at_most_once, boundedness=BOUNDED)
  - jdbc       (delivery=…, boundedness=BOUNDED)
  - mysql-cdc  (delivery=exactly_once, boundedness=UNBOUNDED)
  - postgres-cdc (delivery=exactly_once, boundedness=UNBOUNDED)
```

`make catalog-info` invokes it against the committed catalog. The script can
also be pointed at a freshly-exported catalog to compare two revisions.

### 4. Authoring documentation

A new `docs/catalog-authoring.md` describes:

- When a connector descriptor change requires a catalog regeneration.
- The exact `make catalog-export && git add deployment/catalog/` procedure.
- How to interpret `catalog-check` failures:
  - descriptor drift → re-export and commit
  - build version drift → regenerate against current commit
  - non-determinism → file a bug against `ConnectorInventories.deterministicBytes`
- How to add a new connector (descriptor file → service registration →
  catalog regeneration → CI gate).

The doc cross-references `docs/adr/adr-040-deployment-authoritative-connector-catalog.md`,
`docs/connector-dev.md`, and `.cursor/rules/connector-spi.mdc`.

## Consequences

### Positive

- `catalog-check` no longer drifts on version bumps.
- CI failures carry actionable diagnostics (descriptors added/removed,
  options changed) instead of "files differ".
- Developers can locally inspect the catalog without rebuilding the CLI.
- The author flow is documented and discoverable.
- The catalog-export target is reusable for testing and ad-hoc inspection.

### Negative

- `git rev-parse --short HEAD` requires a git checkout. Container builds that
  use `COPY` without preserving `.git/` will see `unknown` as the build
  version, which is fine because the committed `.pb` will also have `unknown`
  and the gate passes — but the embedded `compiler_build` is then useless for
  provenance. CI runs always have a git context, so the gate is meaningful.
- The diff script depends on `protoc` being available or the Python protobuf
  runtime; the Python path requires the generated `connector.proto` Python
  bindings to be importable. The script falls back to a textual
  `protoc --decode_raw` parser if the binding is unavailable.

## Alternatives Considered

### Read protobuf text-format directly via `protoc --decode_raw`

Pure textual decode avoids the Python binding dependency but produces an
unstable wire format whenever the proto schema evolves. We use it only as a
fallback; the primary path uses the Python binding for stable, typed output.

### Encode the catalog as JSON instead of protobuf

JSON would be inspectable without tooling, but breaks ADR-040's
deployment-authoritative binary catalog contract. The catalog must remain
binary to match the wire format the API server hands to the compiler.

### Reject the hardcoded `--compiler-build` override by removing the option entirely

Removing the option would force the CLI to always embed its own compile-time
`VERSION` constant. That couples the catalog to the CLI jar's build rather
than the project's git state, which is a regression.

# ADR-059: v0.4.0 Release Cut (Phase 17 Observability Activation)

## Status

Accepted

## Context

`CHANGELOG.md` currently has the following top-level sections:

- `## [Unreleased]` — contains **Phase 17** (observability catalog
  backlog activation). All four Phase 17 slices (43.0 umbrella +
  `control-plane/observability/normalize` package, 43.1 api-server,
  43.2 auth library, 43.3 controller) have landed.
- `## [v0.3.0] - 2026-09-07` — Phase 13 through Phase 16.
- `## [v0.2.0] - 2026-09-07` — Phase 1 through Phase 12.

Phase 17's umbrella ADR (ADR-058) records a strict reading of the
catalog backlog as the union of:

  1. every descriptor-only / unregistered business metric in
     `docs/observability/metrics-catalog.md` has a documented
     **Recorder owner**;
  2. every Recorder routes label values through
     `control-plane/observability/normalize`;
  3. every Recorder has a documented **test contract** (table-driven
     happy / rejected / failure paths + scrape-level + non-canonical
     UUID collapse).

Phase 17's `docs/phase17/README.md` writes its acceptance criteria
literally:

  > `metrics-catalog.md` row status updates from "pending" to
  > "emitted" as each slice lands.

That literal reading would block the phase from closing forever:
"emitted" requires observing a non-zero sample in production,
which the project's environment does not yet deploy (Phase 18 +
production rollout has not run). A stricter reading would trap
Phase 17 in `**In Progress.**` indefinitely, even though all the
**design** work (Recorder + normalize + test contract) has shipped.

The release dry-run script (`scripts/release-dry-run.py`) and the
changelog guard (`scripts/check-changelog.py`) are in place per
ADR-057. They need a bump from `0.3.0` to `0.4.0` to reflect the
new content.

Maven `pom.xml` already declares `0.3.0` (post-ADR-057) and Helm
`Chart.yaml` declares `0.3.0`. The version bump is local to those
two files plus the new versioned CHANGELOG section.

## Decision

### 1. Refine the Phase 17 acceptance semantics

The literal "pending → emitted" acceptance criterion is a
**production observation** criterion, not a Phase 17 design
criterion. Phase 17's contribution is **activation** (Recorder
wiring + label-allowlist reuse + test contract). Production
sample observation is the Phase 18 / production-rollout **emission**
criterion.

We adopt the following scope split:

| Phase | Scope | Status gate |
|-------|-------|-------------|
| Phase 17 | Activation: Recorder + normalize routing + test contract + catalog-row owner mapping | All Recorder methods + Owner table + test contract shipped — Phase done |
| Phase 18+ | Emission: production sample observed; row flips "Recorder wired" → "emitted" | Production telemetry pipeline (ADR-051 §7 follow-up) |

The Phase 17 acceptance criterion is therefore **refined** to:

  > `metrics-catalog.md` row status updates from "pending" to
  > "Recorder wired" as each slice lands. The row flips to
  > "emitted" only after a non-zero sample is observed in
  > production; that emission milestone is owned by Phase 18+,
  > not by Phase 17.

With this refinement, **all 12 acceptance criteria are Done** and
`docs/phase17/README.md` flips `**In Progress.**` →
`**Complete.**`.

### 2. Cut `v0.4.0`

Promote the current `## [Unreleased]` content (Phase 17) into a new
`## [v0.4.0] - 2026-09-08` section. Phase 17 ships independently
of Phases 13-16 because Phase 17's contract is orthogonal:
- Phases 13-16 produced a Kubernetes-operable platform artifact
  (production profile, ArgoCD GitOps, catalog lifecycle, CI
  hygiene).
- Phase 17 produces a control-plane observability-activation
  artifact (shared normalize helper + three Recorder contracts).

The two are coherent on their own. Bumping them as a single
release would force a downstream operator to wait for both layers
even if only one is needed; the existing `check-changelog.py`
guard already exempts phases <= 16, so the easiest path is to ship
Phase 17 as its own `v0.4.0`.

A new empty `## [Unreleased]` placeholder is appended so future
slices have a known drop zone.

### 3. Bump the project version

`pom.xml`: `0.3.0` → `0.4.0`. Same rationale as ADR-057 §2 — a
stable release version, not a `-SNAPSHOT` qualifier; the next
post-release commit moves the version to a `-SNAPSHOT` qualifier.

`deployment/helm/astrasync/Chart.yaml`: `0.3.0` → `0.4.0`. Both
`version` (the chart version) and `appVersion` (the application
version) move in lockstep.

### 4. Extend the `check-changelog` exemption

The release-dry-run guard (`scripts/release-dry-run.py`) and the
changelog guard (`scripts/check-changelog.py`) already exempt phases
1-16 per ADR-057. We extend the exemption boundary to
`phase_number <= 17` in **both** scripts so future releases do not
need to touch the guards immediately on opening the next `[Unreleased]`
block. Two changes, both a constant bump from `<= 16` to `<= 17`:

    `scripts/check-changelog.py::main`
    `scripts/release-dry-run.py::phases_missing_from_changelog`

### 5. Release dry-run is the gate

`make release-dry-run` must pass before this ADR is accepted. The
script:
- Reads the Maven version from `pom.xml` (now `0.4.0`).
- Reports the git HEAD that would be embedded in the catalog build id.
- Lists every Complete phase (1, 3-17) and confirms each one
  is referenced in some section of `CHANGELOG.md`.
- Reports the tracked proto file inventory (7 files).

If `release-dry-run` fails, the cut is rejected and the underlying
drift must be fixed before retrying.

### 6. Tagging is left to the maintainer

This ADR does not push a `v0.4.0` git tag (mirroring ADR-057 §4).
Tagging remains the maintainer's release-day action. The
maintainer's checklist:

1. `make release-dry-run` exits 0.
2. `make check` exits 0 (`vet-go + check-runbooks + check-docs +
   spotless:check`).
3. Tag `v0.4.0` against the current commit.
4. Bump `pom.xml` back to `0.4.0-SNAPSHOT` on the next development
   commit (post-release housekeeping, not part of this ADR).

## Consequences

### Positive

- `v0.4.0` ships the Phase 17 activation contract end-to-end:
  shared normalize helper, three Recorder families, test contracts
  on every family, catalog-row owner mapping for every descriptor.
  This unblocks any future work that wants to assume Recorder +
  normalize is a stable contract (e.g. replicating the same shape
  into the Java data-plane emission contract).
- The Phase 17 acceptance refinement clarifies a previously
  ambiguous gating criterion. Future contributors reading
  `docs/phase17/README.md` will not have to re-derive the
  activation-vs-emission split.
- The `metrics-catalog.md` row status now has a precise
  two-stage lifecycle ("Recorder wired" → "emitted") instead of
  a single "pending" / "emitted" toggle, with each stage owned by
  a distinct phase.
- The script exemption extension means the next `[Unreleased]`
  block does not need to commit a `check-changelog.py` change at
  the same time as opening the section.

### Negative

- The `[v0.4.0]` section is comparatively small relative to the
  effort spent on release hygiene. Operators who do not deploy
  control-plane observability gain nothing tangible from the bump.
- The literal "emitted" milestone is now owned by Phase 18+
  with no fixed schedule. If a downstream operator needs the
  "emitted" assurance before their deployment, they may have to
  audit which production sample they need themselves; this is
  honest but not as convenient as a single phase closing both
  halves.
- The Maven chart bump is locked to the appVersion bump; future
  chart-only fixes still need a separate ADR (see ADR-057 §
  "Negative" — this remains unaddressed).

## Alternatives Considered

### Skip the `v0.4.0` cut and keep accumulating in `[Unreleased]`

Reject. Phase 17's Recorder contract is now stable enough that
leaving it in `[Unreleased]` indefinitely would defeat the
purpose of having a release tracking mechanism. The CHANGELOG
*also* plays an audit role: any new metric that references the
shared normalize helper should be able to cite a release line.

### Cut `v0.4.0` only after production samples are observed

Reject. The activation-vs-emission split we adopted here exists
precisely because production rollout is not yet scheduled.
Waiting for "emitted" before cutting release would entangle
release discipline with production-rollout discipline — they are
independent concerns.

### Cut a separate `v0.4.0-alpha` for Phase 17 to mark draft state

Reject. The activation contract is not drafty — every Recorder
has a test contract, every label rule is shared, every catalog
row has an owner. Tagging an `-alpha` release would imply the
contract is not stable enough for downstream consumption; the
existing test contracts argue otherwise.

### Auto-bump versions on release via a `make release` target

Reject for this slice (same rationale as ADR-057 §"Alternatives
Considered"). A `make release` target that mutates `pom.xml`,
`Chart.yaml`, and `CHANGELOG.md` is a worthwhile future ADR but
not in scope for the current release cut.
